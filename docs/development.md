# Developing plan-relay

Repository layout, installing from a clone, building the plugin, the test suites, the extension in development and the execution details. For what plan-relay is and how to start using it, see the [README](../README.md). The paths below start at the repository root.

## Layout


The layers, the direction of the dependencies, the flow from the plan files to the panel and the design principles are in [ARCHITECTURE.md](../ARCHITECTURE.md).

A plugin reads only files from its own folder, which is why the installable is generated: `sh tools/build.sh` joins `core/template/` and `core/scripts/` (without the `tests/`) to the `agents/claude-code/` adapter (skills, `COMMANDS.md`, hooks, manifest, the agent's own scripts in `agent-scripts/` and, in `agent.conf`, the values of the `{{AGENT_…}}` markers that `core/` uses in place of the invocation syntax) into `dist/claude-code/` (pt-BR) and `dist/claude-code-en/` (English), which are versioned so the marketplace reads the repository as it is. The marketplace serves the English package as `plan-relay`, the name a user installs without choosing, and the pt-BR one as `plan-relay-pt-br`. The build writes each package's name into its `plugin.json` and, through the `{{PLUGIN_NAME}}` marker that `AGENT_PLUGIN_SKILL_PREFIX` carries, into the skill prefix: `/plan-relay:plan` in English, `/plan-relay-pt-br:plan` in pt-BR. Another coding agent gets its adapter in `agents/<agent>/` and another panel host gets its folder in `hosts/<host>/`.

The plugin version lives in `agents/claude-code/.claude-plugin/plugin.json` and is repeated in both `.claude-plugin/marketplace.json` entries; they go up together. The extension version lives in `hosts/vscode/package.json`.

## Install the plugin from a clone

The marketplace is the root of this repository and is registered by its **absolute** path. The root `.claude/settings.json` is not versioned: whoever clones the repository registers the marketplace with the commands below.

In a project scope (writes to that project's `.claude/settings.json`), from the project root:

```sh
claude plugin marketplace add /absolute/path/to/plan-relay --scope project
claude plugin install plan-relay@plan-relay --scope project
```

For the skills in pt-BR, install `plan-relay-pt-br@plan-relay` in place of `plan-relay@plan-relay`, here and below. Install one of the two: with both, both sets of hooks run.

In the user scope (writes to `~/.claude/settings.json`):

```sh
claude plugin marketplace add /absolute/path/to/plan-relay --scope user
claude plugin install plan-relay@plan-relay --scope user
```

Check with `claude plugin list --json`: the `plan-relay@plan-relay` entry has `enabled: true` and `readFromFolder` points to `dist/claude-code-en` (`plan-relay-pt-br@plan-relay` points to `dist/claude-code`).

The VS Code extension installs through the same commands, with the package of the VS Code display language: `plan-relay-pt-br` for Portuguese, `plan-relay` otherwise. It recognizes either one as installed and opens the prompts with the prefix of the one it found. The source comes from the `planRelay.marketplace` setting (a folder, `owner/repo` or a git URL); when empty, it comes from the open folder if that is a clone of this repository, otherwise from the `plan-relay` marketplace that Claude Code already knows, otherwise from the public repository over git, which the CLI clones as it is.

Uninstall:

```sh
claude plugin uninstall plan-relay@plan-relay --scope project
claude plugin marketplace remove plan-relay
```

The uninstall leaves `"enabledPlugins": {}` in the settings and the copy in `~/.claude/plugins/cache/plan-relay/`; delete both by hand.

## Develop

Edit the source (`core/`, `agents/claude-code/`), never `dist/`, and generate both packages again:

```sh
sh tools/build.sh
```

The installed plugin reads its package (`dist/claude-code-en/` or `dist/claude-code/`) straight from the folder: after the build, the change reaches the next Claude Code session without `plugin update`. A session that is already open does not see the change; open a new one. CI rejects an outdated package (`sh tools/build.sh --check`).

Validate before testing, at the repository root:

```sh
claude plugin validate --strict .
claude plugin validate --strict dist/claude-code
claude plugin validate --strict dist/claude-code-en
```

Tests of the core scripts (`boundary.sh`, `summary.sh`, `idea.sh`, the general part of `check.sh`):

```sh
sh core/scripts/tests/run.sh
```

Tests of the Claude Code adapter scripts (`window.sh`, the `context-hook.sh` and `plugin-path.sh` hooks, `check.sh` with `check-agent.sh`), of the skill bodies free of agent variables and of the shape of the commands in them (no `$VAR`, `$(…)`, `;`, `&&`), without calling `claude`:

```sh
sh agents/claude-code/agent-scripts/tests/run.sh
```

Tests of the task map template (`status.sh` in text and `--json` over the `core/template/tests/fixture/` fixture, `map.sh`, `README.md` markers):

```sh
sh core/template/tests/run.sh
```

Test of the build (generated tree, `--check`, equal `# scripts_version:` stamps, `{{AGENT_…}}` markers filled in, `core/` without the agent's name):

```sh
sh tools/tests/build.sh
```

The four end in `all good`. The contract conformance suite is `sh core/contract/conformance/run.sh core/template/status.sh` and the edit cases are `sh core/contract/conformance/edit.sh core/template/task.sh`; with `--self-test` in front of the script path, each one also proves it fails on copies broken on purpose, which is how CI runs them. Shellcheck over every `.sh` is `sh tools/tests/shellcheck.sh`, and the local links of every versioned `.md` are `sh tools/tests/links.sh` (offline: links to the web are not followed); both exit 2 when the tool is not installed. CI also lints the workflows with `actionlint` and `zizmor --offline .github/workflows`. CI takes shellcheck, actionlint, zizmor and lychee from `tools/ci-tools.sh`, at the versions written there; locally, the same versions avoid a finding that only one side sees.

### The sh test harness

The sh suites share `tools/tests/lib.sh`, which each one sources by a path relative to itself. It gives `ok`, `ko` and `check <case> <got> <expected>` (a failure prints the case, what it got and what it expected), `exit_of`, `fresh_plan` (a new copy of a fixture plan for each block of cases, so no case depends on what an earlier one left), `deadline <seconds> <pid>` (a background child that does not end in time is killed and the case fails), and `suite_start <name> <seconds> [tool…]`, which refuses with `<name>: needs <tool> on the PATH` (exit 2) when a tool is missing and starts a watchdog that ends a hung suite after `<seconds>`.

`suite_start` also exports a prelude, `TZ=UTC`, `LC_ALL=C.UTF-8` and `HOME` set to an empty folder inside the suite's temporary one, so no case depends on the machine's time zone, locale or home.

Linux is covered in CI without `tools/tests/linux.sh`: the `Plugin` job runs the sh suites on `ubuntu-24.04` as well as `macos-26`. `linux.sh` stays as the local way to reproduce a Linux failure in an Ubuntu container.

For the suites that build a test `PATH` out of links and fake tools, it also gives `tool_path <tool>` (the file on the `PATH`, never the bare name `command -v` prints for a builtin), `path_wins <tool>` and `skip <case> <why>`.

BusyBox needs those last ones. Ubuntu's `busybox-static` builds its `sh` to run its own applets (`uname`, `cat`, `find`…) before it searches the `PATH`, and `command -v cat` prints `cat` instead of a path. So a case that puts a fake `uname` on the `PATH`, or leaves `find` off it, cannot set up what it means to test there. Such a case checks `path_wins <tool>` first and skips with the reason when it is false. The `check.sh` suites skip their system cases and the "without find/cmp" case this way under BusyBox, and still run everything on macOS and on Ubuntu with dash.

BusyBox is checked by hand, not in the CI matrix. Install `busybox-static` and `jq` in an `ubuntu:24.04` container, link the applets you want tested (`awk`, `sed`, `grep`, `date`, `cp`, `sort`, `find`…) to `/bin/busybox` in a folder, put that folder first on the `PATH` and run `sh core/template/tests/run.sh`. The last check (the template suite, scripts_version 20, BusyBox 1.36.1) passed with every case green; the plan scripts read `Started:` in awk, so they do not depend on what the BusyBox `date` accepts. The macOS and Ubuntu runs of the CI stay the promise; BusyBox is only known to work.

The harness is home-made on purpose: the plugin scripts run with `sh`, the POSIX tools and `jq`, and their tests need nothing more, so a contributor runs them on any machine where the plugin runs, and CI installs nothing but `jq` (and `git`, which the `check.sh` suites put on their test `PATH`). The harness itself uses no GNU-only option and runs under dash, bash and BusyBox `sh`. A test framework would be one more dependency to install, pin and keep in step on macOS, Linux and in a container.

**No coverage figure for the sh code.** The tools that measure it, kcov and bashcov, trace a script through bash's `xtrace`: they measure it under bash, not under the dash, macOS `sh` and BusyBox `sh` it runs on, and they bring a toolchain outside the lockfiles (a native build for kcov, Ruby for bashcov). So the sh code has no floor like the TypeScript one. What stands in for it: the conformance suite and the edit cases run against the plan scripts, and `--self-test` proves each one fails on copies broken on purpose, so a suite that stopped checking does not stay green.

CI runs more than these: the whole list, with each command as CI runs it, is in [CI gates](#ci-gates).

Changed a text in `core/i18n/`? Run `sh tools/script-strings.sh` without `--check` to rewrite the blocks and, if the text belongs to `status.sh`, `task.sh` or `map.sh`, bump the `# scripts_version:` stamp of the three scripts.

The task header is read and rewritten in one place, `core/template/header.awk`: functions that `tools/script-strings.sh` embeds as `HEADER_AWK` between `# >>> header` and `# <<< header` in `status.sh`, `task.sh`, `map.sh` and `boundary.sh`, whose awk programs start with `"$HEADER_AWK"`. The copies in a plan stay self-contained. A change there means running `sh tools/script-strings.sh` and bumping the stamp; `tools/tests/header.sh` fails when a script reads `Status:` outside the block.

The plugin scripts that run outside a plan (`check.sh`, `boundary.sh`, `idea.sh`, `summary.sh`, `selftest.sh`, `copy.sh`, `profile.sh` and the adapter ones) speak the package's language. In the source they have the line `language='{{PACKAGE_LANGUAGE}}'`, which `tools/build.sh` replaces with `pt-BR` in `dist/claude-code/` and with `en` in `dist/claude-code-en/`. A new text in one of these scripts goes into `core/i18n/` (or into `agents/claude-code/i18n/`, if the script belongs to the adapter), in all three languages, under an English key name (`tools/tests/no-pt-in-code.sh` checks it), and comes out through the script's `msg <key>`; `tools/tests/no-pt-in-en.sh`, run by `tools/tests/build.sh`, flags pt-BR text outside comments in the scripts of the English package. To prove nothing was left hardcoded, the tests run a copy with `language='x-test'`.

Quick check, in a new session of the project where it is installed: `/plan-relay:map <plan.md>` presents the task map design and waits for approval before writing. `/plan-relay:run agent_plans/<name>` runs the preflight (`summary.sh`, `boundary.sh`, `window.sh --read`, `check.sh --json`) and stops at the briefing with the questions to the owner. `/plan-relay:check` shows what the environment lacks (jq, git, CLI, login, plugin up to date) and how to fix it.

### CI gates

The single list of what CI runs (`.github/workflows/ci.yml`), job by job, each command as the workflow runs it from the repository root. `sh tools/tests/gates.sh` fails when the workflow runs a command that is not here or this list names one it does not run; the pull request template points here. Before a pull request, run what your change touches; CI runs it all.

To run the whole list in one go, after `npm ci --ignore-scripts`:

```
sh tools/gates.sh
```

It runs each command below from the repository root, in order, and prints one line per gate, with the seconds it took: `ok`, `FAILED` (with the end of its output) or `skipped` (with the missing tool and how to get it). It exits 0 only when every gate passed. A missing shellcheck, actionlint, zizmor or lychee is fetched with `tools/ci-tools.sh` (the pinned version, checked by sha256, for Linux x86-64 and macOS) into a temporary folder, so nothing is installed; on macOS, or with a display already set, the integration run goes without `xvfb-run`. Any other missing tool (`claude`, for example) skips its gates, and a skip fails the run unless you pass `--allow-skip`.

```sh

xvfb-run -a npm run test:integration

# Plugin (sh suites), on macOS and Ubuntu

sh agents/claude-code/agent-scripts/tests/run.sh
sh core/template/tests/run.sh
sh tools/tests/build.sh
sh tools/tests/languages.sh             # every pt-BR text has its English pair in the en/ folders
sh tools/tests/versions.sh              # every package has the same version in all manifests (tools/versions.sh)
sh tools/tests/release.sh               # the release logic (tools/release.sh) with a fake gh
sh tools/build.sh --check               # dist/ is the build of core/ and agents/claude-code/
```

## Extension

The `plan-relay` VS Code extension (`hosts/vscode/`) reads the plans in `agent_plans/*/plan.json` of each workspace folder and shows them in a panel in the secondary sidebar (on the right). Users install it from the marketplace as `saboyafelipe.plan-relay` (see the [README](../README.md#first-use)); to try a change from a clone, build and install a local `.vsix` as below. The two share the extension ID, so uninstall one before installing the other.

### Install the extension from a clone

At the repository root, with the Node version in `.nvmrc` (`nvm use`; CI reads the same file, and `engines.node` in the root `package.json` matches it):

```sh
npm install
npm run package
code --install-extension hosts/vscode/plan-relay-<version>.vsix
```

`npm install` installs the npm workspaces (the core packages and the extension) in a single `node_modules` at the root. `npm run package` compiles and writes `hosts/vscode/plan-relay-<version>.vsix` (the version is the one in `package.json`) with the `package.json`, `dist/` and `media/`; it runs without prompts.

Uninstall:

```sh
code --uninstall-extension saboyafelipe.plan-relay
```

### Use

The panel opens by itself the first time a workspace with plans activates the extension; after that, through the «Plan Relay» icon in the secondary sidebar or through «Plan Relay: Show panel». In a folder without plans it does not open by itself: open it through those two ways (for example, to install the plugin before creating the first plan). It refreshes when the task files change, every `planRelay.refreshIntervalMinutes` (5 by default; 0 turns it off) and through the «Refresh» icon in the view's title bar.

**In the Agents window** (`code --agents`), which does not show extension views, the panel opens as an editor tab, the first time and through «Plan Relay: Show panel»: the extension declares `capabilities.agentsWindow.supported` and, without the `workbench.view.extension.plan-relay` command, uses a `createWebviewPanel` with the same page (`hosts/vscode/src/surface.ts`). The key is newer than the `engines.vscode` floor: VS Code 1.106 does not have it in the `capabilities` schema and ignores it without error, and 1.146 has it; the Agents window itself reached Stable, as a preview, in the May 2026 release. «Run» and «Run plan» still rely on the official Claude Code extension, which does not exist in that window.

- **View title bar:** «Search», «Refresh» and, on the Plans tab, «Collapse all». Its «⋯» menu holds «Plugin status…» (the state of the `plan-relay` plugin for the first folder of the workspace and the time of the last refresh), «Install the plugin» (you choose the scope: project or user), «Uninstall the plugin» and «5-hour window gate…».
- **Top:** only when something needs you: the plugin missing, outdated, installing or failing (with «Install» when it is missing; while it installs, the button reads «Installing…»), or a notice from the extension. With everything in order there is no top.
- **Tabs:** «Now», «Plans» and «Ideas», each with a counter.
- **Now:** across plans, the tasks in progress («Resume»), those waiting on you, the free ones («Run», with a mark when one can run in another session) and what unblocks next. Its counter is highlighted when a task waits on you.
- **Plans:** one card per plan, with name, badge (`done`, `run open`, `needs you`, `in progress`, `idle`), a stacked progress bar with a legend, «Run plan» and «Map» (and «Log» while a run has one), and a «⋯» menu with «Open PLAN.md», «Open MAP.md», «Open README.md», «Copy run command» and «Delete plan…». Below, the phases (completed and abandoned ones folded into blocks of their own) or, switched in the filters, the tasks by state.
- **Ideas:** `agent_plans/_ideas/` by state, with «Refine», «Create tasks», «New idea» and «Open folder».
- **Search and filters:** each tab has a search box; «Plans» filters by track and tier, «Now» by plan. With a filter on, only what matches stays, and clearing it brings back what was open.
- **Task detail:** clicking a task opens a dialog with its header fields, next step, «Depends on» and «Unblocks» (each ID clickable) and the actions.
- **Footer:** what the environment lacks (`jq`, the CLI…) or what needs attention, with the detail in the «Plan Relay» output channel.
- **Create tasks from a document:** right-click a `.md` in the explorer outside `agent_plans/`, «Create tasks from this plan» (or the same command from the palette, with the `.md` in the editor). If that file already produced a plan, the extension offers to open it or to delete it and map again.

Each action puts a prompt in the agent's box (today, Claude Code), without sending it: «Run» and «Resume» open `/plan-relay:plan <plan> <ID>`, «Run plan» opens `/plan-relay:run agent_plans/<plan>`, and «Create tasks» opens `/plan-relay:map <path of the .md>`. Without the official Claude Code extension (`anthropic.claude-code`), the prompt goes to the clipboard and a notification asks you to paste it. «Delete plan…» moves the plan folder to the trash, after a warning. The three actions need the plugin: without it, the extension offers to install it first. What belongs to the agent (detecting it, installing the plugin, opening with a prompt, building the prompt) lives in a provider, in `hosts/vscode/src/agents/`; the Claude Code one is in `agents/claude-code/`.

Warnings:

- **Trust the workspace.** The extension reads the plans' state in TypeScript (`core/reader`), without running `status.sh`, but it runs the Claude Code binary from the workspace folders, so it does not run in restricted mode: the panel only appears after you trust the workspace («Restricted Mode» in the status bar, or the dialog on opening). The official Claude Code extension also only loads in a trusted workspace.
- **Claude Code adds the active editor to the context.** The conversation the action opens receives the file open in the editor (or the last visible one); close what you do not want before clicking, so it is not carried along.
- **With several folders, the session opens in the first.** Claude Code opens the session in the first workspace folder; a plan in another folder gets a warning, because the prompt's paths may not exist there. To work on that plan, open its folder as the first (or only) one.

### Develop

At the repository root, with the Node version in `.nvmrc` (`nvm use`; CI reads the same file, and `engines.node` in the root `package.json` matches it):

```sh
npm test             # vitest, the pure modules and the webview, of the extension and the core
npm run coverage     # the same suite with v8 coverage; fails below the floor of any package
npm run typecheck    # TypeScript 7, tsc -b over the project references
npm run lint         # ESLint (typescript-eslint, recommended with type information, and the boundary of each layer) in hosts/vscode/src and in the core
npm run format:check # Prettier; npm run format rewrites
npm run build        # esbuild → dist/extension.js and dist/webview.js
npm run test:integration # a real VS Code with the extension (below)
```

**Coverage floors.** `vitest.config.mts` sets a floor per package (lines/branches/functions), equal to what was measured and rounded down: `core/i18n` 100/100/100, `core/reader` 97/90/100, `core/panel` 94/90/97, `hosts/vscode` 92/87/86. The CI job `extension` runs `npm run coverage` and prints the summary. To raise a floor, edit `coverage.thresholds` in `vitest.config.mts` to the new measured value (rounded down) in the same change that adds the tests; never lower one to make a change pass. The tests run with `isolate: false`, so a test must not leave state in a module for the next file.

**The host in the unit tests.** The `vscode` module only exists inside the editor, so `vitest.config.mts` aliases it to `hosts/vscode/src/testing/vscode.ts`: a fake of the slice of the API the host uses, which records what the host did (messages shown, commands registered, the webviews and what was posted to them) and lets a test answer the questions (`fake.answer`, `fake.pick`). It is one instance for the whole run: `fake.reset()` starts over.

`activate` composes the host (strings, output channel, alerter, sound) and creates nothing on import, so `activateHost()` in `testing/context.ts` starts a fresh host on the fake, and a test drives it as VS Code would: `fake.resolveView(VIEW)` shows the sidebar view, `fake.run('planRelay.show')` runs a command, `view.webview.receive(message)` is a message from the page. The fake is outside the coverage count.

**Integration test.** `npm run test:integration` compiles the extension and `src/integration/` (into `out/integration/`, outside the `.vsix` and vitest), downloads with `@vscode/test-electron` the VS Code at the minimum version of `engines.vscode` into `.vscode-test/` (~150 MB the first time) and opens it with the extension in development over a temporary copy of `fixtures/demo-project/agent_plans/`, in two rounds: the copy as it is and the copy in a `git init` with `agent_plans/` in `.gitignore` (the search of a `workspaceContains` with a glob respects the ignore files and `files.exclude`; `workspaceContains:agent_plans`, without a glob, is checked without a search).

In each round, the suite (`src/integration/suite.ts`) checks that the extension activates by itself through `workspaceContains`, that the public commands exist and that «Run» on a task of the example hands `/plan-relay:plan <plan> <ID>` to the agent. The agent is simulated without changing the extension: `planRelay.claudePath` points to a fake `claude`, which only answers `plugin list --json` (active plugin), and the suite registers the command of the official Claude Code extension, which is not installed in the test VS Code.

On macOS it opens a window for a few seconds; on a Linux without a display, `xvfb-run -a npm run test:integration` (which is what the CI job `integration` runs). The runner clears `ELECTRON_RUN_AS_NODE`, so it also runs from a VS Code terminal. Raising `engines.vscode` raises the test version and the CI cache key.

**The core boundary.** `core/i18n`, `core/reader` and `core/panel` are npm workspaces (`@plan-relay/i18n`, `@plan-relay/reader`, `@plan-relay/panel`): the extension imports each by name, and the `exports` of each `package.json` says what is public (`@plan-relay/reader/node` is the Node side of the reader; `@plan-relay/reader/testing`, the test fixture). Each package is a `composite` project with references only to the packages it depends on, so a core file that imports from `hosts/` or from an undeclared package does not compile (TS6307), and `core/panel` and `core/i18n` compile without the Node types.

`eslint.config.mjs` completes it with `no-restricted-imports` per layer: `vscode` forbidden in all of core; Node modules (`node:*` and the bare built-ins) and `@plan-relay/reader/node` forbidden in the code of `core/panel` and `core/i18n` (the tests run in Node and may read files); in `core/reader`, Node modules only in `src/node.ts` and the test fixture in `src/testing/`, so the rest of the reader stays importable in the browser. `hosts/vscode/src/architecture.test.ts` proves the rule with refused and accepted cases, and covers what it does not see: `import('vscode')` and `require('vscode')`.

Lint and format cover `hosts/vscode/src` and the core's TypeScript, running from the root; Prettier reads the root `.prettierrc.json` and `.prettierignore` (code only: `.md` and `.json` stay out). CI runs both in the `extension` job. Style belongs to Prettier alone; ESLint has no style rule.

- **Two TypeScripts.** `typecheck` uses TypeScript 7 (the `typescript-7` package, an alias of `typescript@7`). The name `typescript` points to `@typescript/typescript6`, because `typescript-eslint` still needs the TypeScript 6 JavaScript API, which 7 does not have (its peer range is `typescript >=4.8.4 <6.1.0`, rechecked with `npm view typescript-eslint peerDependencies` at 8.72.2; the type-aware lint runs on that 6); that is why `npx tsc` gives 6. When `typescript-eslint` accepts 7, the alias goes away and `typescript` becomes 7 again.
- **CLI version in CI.** The `plugin-validate` job installs `@anthropic-ai/claude-code` from its own lockfile, `tools/claude-cli/`, with `npm ci --ignore-scripts`, and puts the folder of the Linux x86-64 native binary on the `PATH`: the package's install script only links that binary over a stub, so skipping it loses nothing. Dependabot opens the PR that raises the version; before merging it, run `claude plugin validate --strict .`, `claude plugin validate --strict dist/claude-code` and `claude plugin validate --strict dist/claude-code-en` with the new version (locally: `npm ci --ignore-scripts --prefix tools/claude-cli`, then the `claude` in the `@anthropic-ai/claude-code-<platform>` folder of `tools/claude-cli/node_modules/`). The version is exact so that a new `--strict` warning does not break CI without a change in the repository.
- **Linter versions in CI.** `tools/ci-tools.sh` pins shellcheck, actionlint, zizmor and lychee by version and sha256, and Dependabot does not see them. To raise one, change the version and the digest together (the command that lists the digests of a release is in the script's header), then run the gate with the new version locally.
- **Security advisories.** CI fails on any advisory in the dependencies that reach the `.vsix` (`npm audit --omit=dev --audit-level=low`); the development ones are left to Dependabot alerts, so an advisory in a build tool does not block CI or a release. The root `package.json` and `tools/publish/package.json` override `minimatch` to `^11.0.1`: `@vscode/vsce` 4.1.1 and `typescript-eslint` 8.72.2 still ask for `^10`, which has GHSA-g3hv-75wg-m249. Proved with lint, `npm run package` (the same 15 files in the `.vsix`) and `npm audit` at 0. When both parents ask for 11 by themselves, the override goes away. Do not run `npm audit fix --force`: its fix is to downgrade both parents by a major.

The Extension Development Host opens through `launch.json` (F5 in VS Code, with the `hosts/vscode/` folder open), which compiles and opens `.vscode/dev-host.code-workspace`, pointing at the demo project fixture in `fixtures/demo-project/`. Outside VS Code:

```sh
code --extensionDevelopmentPath=<extension> --new-window <extension>/.vscode/dev-host.code-workspace
```

With the normal profile, a folder already open in another window does not open in the host; the workspace is another identity and opens. In an environment with `ELECTRON_RUN_AS_NODE` set (a terminal that inherits it from VS Code), VS Code does not start: run `env -u ELECTRON_RUN_AS_NODE code …`. What the extension does goes to the «Plan Relay» output channel.

## Publish a version

The repository has two packages, each with its own version and its own tag:

| Package | Tag | Manifests with the version |
|---|---|---|
| `vscode` (the extension) | `vscode-vX.Y.Z` | `hosts/vscode/package.json` and the root `package-lock.json` (in `packages["hosts/vscode"]`) |
| `claude-code` (the plugin) | `claude-code-vX.Y.Z` | `agents/claude-code/.claude-plugin/plugin.json`, the copies in `dist/claude-code/` and `dist/claude-code-en/`, and `plugins[].version` of both `.claude-plugin/marketplace.json` entries (`plan-relay` and `plan-relay-pt-br`) |

The plugin version is not the `scripts_version` of the plan scripts: that one goes up only when `status.sh`, `task.sh` or `map.sh` change.

1. Raise the version in all the package's manifests. For the extension, at the root: `npm version X.Y.Z --no-git-tag-version --workspace=hosts/vscode` (changes the extension's `package.json` and the root lock together). For the plugin: edit `agents/claude-code/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`, and run `sh tools/build.sh` for the `dist/` copies.
2. Replace the title of the CHANGELOG's `## [Unreleased]` section with the version, with the date, and open an empty `[Unreleased]` above it. The extension uses `## [X.Y.Z] - YYYY-MM-DD` in `hosts/vscode/CHANGELOG.md` (which is what the store shows); the plugin uses `## [claude-code-vX.Y.Z] - YYYY-MM-DD` in the root `CHANGELOG.md`, and the extension's part of that file goes to a `## [vscode-vX.Y.Z]` section. The GitHub Release notes are the body of that section, and the release refuses when it is missing or empty.
3. Check: `sh tools/versions.sh` exits 0 and lists the version of each package; when something diverges, it says which manifest and with what value. `sh tools/release.sh notes vscode-vX.Y.Z` (or `claude-code-vX.Y.Z`) prints the notes the release will use.
4. Commit with the manifests and the CHANGELOG.
5. Tag the package, checked beforehand: `sh tools/versions.sh --tag vscode-vX.Y.Z` (or `claude-code-vX.Y.Z`) exits 0, and then `git tag vscode-vX.Y.Z` and the tag push.

`sh tools/versions.sh --version <package>` prints the package version, for scripts and workflows.

### What the tag triggers

Pushing the tag runs `.github/workflows/release.yml`; no other workflow fires on a tag.

- **`vscode-vX.Y.Z`:** the `check` job runs `sh tools/release.sh info` (well-formed tag, version equal to the manifests', pre-release or not) and `notes`; the `ci` job calls `ci.yml` at the tag, the same workflow and gates as a pull request, with no npm or VS Code cache, and its extension job packages the `.vsix` (as a pre-release when the minor is odd); then, in parallel, `github` creates the GitHub Release with the `.vsix` and the notes, `marketplace` publishes to the Visual Studio Marketplace and `openvsx` publishes to Open VSX. The two store jobs install `vsce` and `ovsx` from `tools/publish/` with `npm ci --ignore-scripts`, nothing else.
- **`claude-code-vX.Y.Z`:** `check`, the same `ci` job and `github`, which creates the release with the notes only. The plugin installs through the git marketplace, which reads the repository at the tag; there is no store and no attachment.

Nothing publishes unless every CI job is green at the tag.

The `github` job also attests the build provenance of the `.vsix` (`actions/attest`; only when the repository is public, since attestations need it). Whoever downloads the file from the Release checks that it came from this workflow, at this tag, with `gh attestation verify <file>.vsix --repo <owner>/<repo>`.

**Pre-release: odd minor.** The Marketplace accepts only `X.Y.Z`, with no suffix such as `-rc.1`; the pre-release is a flag on the `.vsix` (`vsce package --pre-release`). For the extension, a version with an odd minor (`0.1.x`, `0.3.x`, `1.1.x`) goes out as a pre-release on both stores and on the GitHub Release; an even minor (`0.2.x`, `1.0.x`) goes out as a normal version. This is the VS Code documentation's recommendation; whoever picks «Switch to Pre-Release Version» on the extension page starts receiving the pre-releases. A normal version and a pre-release never share the same number. The first publication, `vscode-v0.1.0`, goes out as a pre-release; the first normal one will be `0.2.0`. The plugin has no pre-release.

**Credentials.** The Marketplace keeps no token: the publisher has a Trusted Publishing policy that trusts this repository's `release.yml`, in the `release` environment, and the job exchanges the GitHub OIDC token for a 15-minute credential (`vsce publish --oidc`). Open VSX uses the `OVSX_PAT` secret of the `release` environment; without it, `ovsx` tries Open VSX's trusted publishing. Open VSX only registers a trusted publisher for an extension that already has a version published with a token, so the first publication needs `OVSX_PAT`; after it, the secret can go. The names are in the comment at the top of the workflow.

### Redo a publication that failed

One store may fail and the other not (for example, Open VSX published and the Marketplace refused). After fixing the cause (credential, policy, name), run the workflow by hand on that same tag: in the Actions tab, «Release» → «Run workflow» → «Use workflow from» = the tag `vscode-vX.Y.Z` and `tag` = `vscode-vX.Y.Z`, or `gh workflow run release.yml --ref vscode-vX.Y.Z -f tag=vscode-vX.Y.Z`. Run it on the tag, not on `main`: the `release` environment only allows the `vscode-v*` tags, and it checks the ref the run was started on, not the `tag` input.

The workflow redoes the check, the CI and the `.vsix` from the tag (run on the tag, the workflow files are the tag's too); each store skips the version it already has (`--skip-duplicate`), and the GitHub Release that already exists only receives the `.vsix` again. If the cause was in the code, it is not redone: raise the version and a new tag goes out (a published version cannot be replaced in the stores).

## 5-hour window

The autopilot (`/plan-relay:run`) can stop launching when the subscription's 5-hour quota passes the threshold chosen at preflight, and wait for it to renew. This is opt-in: the probe is off until you set `PLAN_RELAY_WINDOW=on` in the Claude Code environment, for example `"env": {"PLAN_RELAY_WINDOW": "on"}` in `settings.json`.

The extension does it for a project: «Plan Relay: 5-hour window gate…», in the panel's «⋯» menu, shows the value it reads from `.claude/settings.local.json` of the first workspace folder and, on your choice, writes `env.PLAN_RELAY_WINDOW` there (`"on"`) or removes it, keeping every other key; a file that is not valid JSON is left untouched. It writes nothing on its own, and the change applies to Claude Code sessions opened afterwards (`hosts/vscode/src/agents/claude-code/window-gate.ts`).

Without the variable, `window.sh` answers `status=off` without calling anything. To know the usage, `window.sh` makes a real call to Claude Code (`claude -p --model haiku`, with no tools, MCP, plugins or skills, and a one-line system prompt; the reply is two letters) at most every 5 minutes, and reads the `rate_limit_event` that comes in the stream. Each probe counts against the quota: about a thousand input tokens and 4 output tokens.

It only makes sense for those who use Claude Code through a subscription (Pro, Max); with an API key there is no 5-hour window, and the probe only spends. So, with `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` set in the environment (an API key, a proxy, or the VS Code Agents window, which uses the Copilot account), `window.sh` does not probe and answers `status=no-subscription`; the value of those variables is never read.

The call is killed after 60 seconds (`PLAN_RELAY_WINDOW_TIMEOUT`, in seconds) and `window.sh` answers `status=timeout`. The event is not documented: if the format changes, or the cached `resetsAt` is not a number, `window.sh` answers `status=unknown-format` instead of data, and the autopilot goes on without the gate. To turn it off again, choose «Off» in that action, remove the variable, or choose «off» at the preflight window question. When off, the briefing warns that the run goes without this gate.

## State of the scripts

`window.sh` and `context-hook.sh` keep their state in the directory given by `--data <dir>`, otherwise in `CLAUDE_PLUGIN_DATA`, otherwise in the default folder `${XDG_STATE_HOME:-~/.local/state}/plan-relay/`. The hook receives the variable in its environment and writes to `~/.claude/plugins/data/plan-relay-plan-relay/`; a skill's `Bash` calls do not inherit it, and the skill runs `window.sh` without `--data`, which is why the window cache lives in the default folder.

No skill cites `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` or `${CLAUDE_SKILL_DIR}` in its body: Claude Code substitutes them, but another agent (ZCode, see [ARCHITECTURE.md](../ARCHITECTURE.md)) leaves them literal. The plugin path arrives through the `plugin-path.sh` hook, which runs on `SessionStart` (also after a compaction) and on `SubagentStart` and puts the line `plan-relay plugin root: <path>` in the context; the skills write `<plugin>` where that path goes. Without the line, `map`, `run`, `check`, `idea` and `refine` stop and ask for a new session with the plugin enabled; `plan` and `handoff` go on anyway, one literal command per call, because they only need the scripts the plan carries.

- `window.sh`: cache in `<data>/window.json`.
- `context-hook.sh`: only acts in a project with `agent_plans/` (in the session's `cwd` or in `CLAUDE_PROJECT_DIR`); in the others it exits right away, without reading the transcript or creating a file. Marks `<data>/context-<session>-<level>`, with the level `near` or `over-<n>`, and those older than 7 days are deleted when the hook writes a new one.

  The limit in tokens comes from `PLAN_RELAY_CONTEXT_LIMIT`, 150000 by default, which fits a 200k window; warning at 90 % and then every 50k above. With a 1M window, set the variable in the Claude Code environment, for example `"env": {"PLAN_RELAY_CONTEXT_LIMIT": "500000"}` in `settings.json`. The hook's JSON is read with `jq`, and with `sed` when there is no `jq`.

## Plans in a git repository

When the project root is a git repository, the plan is versioned with the code (the «Version control» section of `core/template/README.md`): the `map` skill makes the first commit of the plan folder, each work session commits the plan files it changed apart from the deliverables, and the conductor commits the journal at closing and at the handoff. Always by named paths; never a push.
