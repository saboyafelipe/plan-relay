# How to contribute

Thanks for your interest. This guide explains how to open an issue or a pull request and what a contribution is expected to look like. For the repository layout, the build and the test suites, see [docs/development.md](docs/development.md), which is the source of those commands.

By taking part, you accept the [Code of Conduct](CODE_OF_CONDUCT.md).

## Language

The project's text (documentation, messages, skills, panel) exists in Brazilian Portuguese, addressing the reader as "você", and in English. Public identifiers (names of skills, settings, commands, plan contract keys) are in English. Issues and pull requests may be written in either language.

## Issues

- **Security flaw:** do not open an issue. Follow [SECURITY.md](SECURITY.md).
- **Bug:** use the "Bug" template. Give the extension and plugin versions, the agent, the system, the steps, what you expected and what happened. The output of `/plan-relay:check` helps.
- **Idea:** use the "Idea" template. Start with the problem, not the solution.

Before opening one, look for a similar issue.

## Pull requests

For a big change, open an issue first and agree on the design: it saves work on both sides.

1. Fork and create a branch from `main`.
2. **Test first.** A new rule is born with the test that proves it: the test goes red, the code makes it green, and only then do you refactor. A fixed bug gets the test that reproduced it.
3. **Edit the source, never what is generated.** The plugins in `dist/` are generated by `sh tools/build.sh` from `core/` and `agents/claude-code/`. Changed one of those? Run the build and put the generated `dist/` **in the same commit**. CI rejects an outdated `dist/`.
4. **Text in both languages.** Translatable pt-BR text has its English pair in the `en/` folder next to it, and the public documents (`README`, `CONTRIBUTING`, `SECURITY`, `CODE_OF_CONDUCT`) come as `X.md` (English) and `X.pt-BR.md`; CI checks the parity.
5. **Accessibility is a requirement.** A change in the panel keeps what the [Accessibility](README.md) section of the README promises. A new view or control gets its case in `core/panel/src/axe.test.ts` (no axe violation) and, if it has a state or an action, in `core/panel/src/a11y.test.ts` (reachable by keyboard, not told only by color); a new color is a `--pr-*` variable that each host maps to its theme, never a fixed one.
6. **Run what CI runs:** `sh tools/gates.sh`, after `npm ci --ignore-scripts`, runs every gate and exits 0 only when all pass. The single list is [CI gates](docs/development.md#ci-gates) in docs/development.md, with each command as CI runs it; run at least the gates your change touches, and the whole list before a pull request.
7. **Commits that name the files.** `git add <file> <file>`, never `git add -A` or `git add .`. The message says what changes and why.
8. Open the pull request against `main` and fill in the template.

## Commit messages

- A short subject, in English and in the imperative mood ("Add the retry test", not "Added" or "Adds").
- A body that says why the change is needed, when the subject does not already make it clear.
- One commit per logical change.
- No internal references: task IDs, decision numbers or paths to planning files do not belong in a message, nor in code, comments or documentation.

## What stays out of the repository

- Paths from your machine (your home folder, your user name). In fixtures and examples, use neutral paths such as `/home/dev/projeto`.
- Names of companies, clients or internal projects, account identifiers, prices, emails or other personal data.
- Secrets of any kind (tokens, keys, passwords), even in tests.
- Your work plans: the root `agent_plans/` is in `.gitignore` (the ones in the test fixtures, such as `fixtures/demo-project/`, are versioned on purpose).
